# RattlerRadar

## Getting Started

```bash
cp .env.example .env   # then fill it in (see "Sign-in" below)
bun run db:push              # creates data/rattlerradar.db
bun run sync:rattlertracks   # saves and tags events (needs TYPESAFE_AI_API_KEY)
bun dev
```

Open [http://localhost:3000](http://localhost:3000) with your browser to see the result.

## How events get to the page

```
RattlerTracks API
  → src/lib/rattlertracks/        fetch + validate + normalize (RattlerTracksEvent)
  → src/lib/events/tag-event.ts   tag with Jev: tags, audience, free food/stuff
  → src/lib/event-store.ts        save/load the event tables
  → src/lib/events/get-event-feed.ts
                                  upcoming events only, sanitized, formatted
                                  in campus time (FeedEvent), cached for an hour
  → src/app/page.tsx              home page
  → src/components/event-feed/    search, filters, cards, details panel
```

**Tags:** `src/lib/interests.ts` is the one tag list, used for onboarding,
filter pills, search, and scoring. Jev (TypeSafe AI's decision model) asks
one yes/no question per tag about each event's title, hosts, location, and
description; RattlerTracks' own themes and categories are ignored. Only new
or changed events are sent to Jev on each sync. After changing the tag list
or questions, bump `TAGGER_VERSION` and run `bun run tag:events` (prints
each event's tags for spot-checking; `--all` re-tags everything).

**Daily sync:** Vercel Cron calls `/api/cron/sync` every day at 12:00 UTC
(6 AM campus time in winter, 7 AM in summer; see `vercel.json`). It runs
the same code as `bun run sync:rattlertracks` (`src/lib/sync-rattlertracks.ts`)
and then clears the feed's cache so new events show up right away. The route
only accepts Vercel's `Authorization: Bearer $CRON_SECRET` header, so set
`CRON_SECRET` in the Vercel project's environment variables. Run logs are in
the Vercel dashboard under the project's Cron Jobs / Logs.

`src/lib/rattlertracks/` uses the JSON API behind the RattlerTracks website.
That API is undocumented and disallowed in robots.txt, so the client keeps
traffic minimal and validates every response, failing loudly if the format
changes.

## Sign-in

Google sign-in via [Better Auth](https://www.better-auth.com) with its default
settings, with users and sessions stored in SQLite through Drizzle. Sessions
last 7 days and extend automatically while someone keeps using the app.

| File | Role |
| --- | --- |
| `src/lib/auth.ts` | Better Auth config (Google provider) |
| `src/lib/session.ts` | `getSession()` / `requireSession()` for pages and server actions |
| `src/app/sign-in`, `src/app/account` | Sign-in page and the first account-only page |
| `src/db/` | Drizzle client and schema (`schema/auth.ts` is generated) |

To make a page account-only, call `requireSession()` in it.

**Google credentials:** in Google Cloud Console, create an OAuth client ID
(type "Web application") with the redirect URI
`http://localhost:3000/api/auth/callback/google`, then put the client ID and
secret in `.env`.

**Database:** `DATABASE_URL` is a local file in development. To use Turso,
set it to the `libsql://…` URL and add `DATABASE_AUTH_TOKEN`; no code changes.
There are no migration files: `db:push` syncs the database to the schema.

```bash
bun run auth:schema   # regenerate Better Auth's tables after changing its config
bun run db:push       # apply schema changes to the database
```

## UI

Components come from [shadcn/ui](https://ui.shadcn.com) (Mira style, themed in
`src/app/globals.css`). Files in `src/components/ui/` are generated by the
shadcn CLI and are excluded from linting; add more with
`bunx shadcn@latest add <component>`.
